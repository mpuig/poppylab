# Personal Agent Protocol 1.0

Iris, Juniper, Lantern, Harborline, Northwind and Fernwick implement **only** Poppy 1.0, published 14 November 2026, and version 3 of the Operations extension. There is no compatibility with 0.1–0.4: a document of another version is refused ("Unsupported Poppy version"), and runs saved by the 0.3 implementation are discarded, not migrated. The text is pinned in `spec/1.0/` (spec, Operations extension, guides); `pnpm spec:drift` reports when the published text changes.

1.0 is 0.4 with the fixes implementers needed. Coming from 0.3, both releases changed what's on the wire. What Poppy Lab does now, section by section:

## Discovery and versions (§3)

- `poppy.json` has `protocol_version: "1.0"`. Iris takes the newest compatible document (any 1.x) among `protocol_version` and `supported_versions`. A linked document must be on the host that served `poppy.json`, is fetched without redirects, has the version it's listed under and no `supported_versions` of its own.
- `organization.domain` is the served host **with its port when it isn't 443**. Locally that includes `juniper.localhost:4100`, `noodles.localhost:4200`, `harbor.localhost:4300`, `northwind.localhost:4400` and `fernwick.localhost:4500`. Iris uses another port only for these exact local Companies, in development.
- Every request with the Session header carries `Poppy-Version: 1.0`. The Companies refuse a missing or incompatible version with `version_unsupported`; Iris then stops, because it implements 1.0 only.
- Extensions are listed per version (`"operations": [{ "version": "3" }]`) and declared per request: `Poppy-Extensions: "operations";v="3"`. Iris declares only what the Company lists, and `poppylab.dev/fdx` only with Use FDX on. Client metadata no longer has `extensions`. The Companies' gateway reads every declared extension and version. A Company can name the extension a route needs, and a request that doesn't declare that version gets `extension_required` (HTTP 403, JSON body); Operations v3 is in use everywhere, and Harborline also lists `poppylab.dev/fdx` v1 for its FDX-shaped API ([Harborline](harborline-bank.md#fdx-shaped-api)).
- Discovery keeps, in the Company profile's `extensions`, the entry of each extension version the client library supports: Operations v3, `poppylab.dev/fdx` v1 when its `base_url` and `consent_endpoint` are HTTPS URLs on `organization.domain`, and `poppylab.dev/espi` v1 when its `resource_endpoint` is (plain HTTP only for the local Companies). The ESPI-shaped entry has native tools in the client library ([ESPI-shaped APIs](openapi-tools.md#espi-shaped-apis-a-native-adapter)). An entry that fails that check counts as not listed, and the Inspector trace says why. Iris declares and uses the FDX entry only when the User turns on **Use FDX** for a conversation, and the ESPI entry only with **Use ESPI** on. Switching it starts a new Session, because declarations are fixed for a Session (§3.4) ([Use FDX](openapi-tools.md#in-the-playground-use-fdx-and-use-espi)). A profile saved before profiles kept `extensions` has none, so the control doesn't appear for it.
- Every `agent.protocols` entry has a `description` of what the agent there helps with. A document without one fails discovery.
- Scopes come from the issuer's `scopes_supported` or the resource metadata's, or both. The Companies list theirs in both.
- Excluded tasks moved behind `tasks.endpoint` (§9): Iris reads it early in each Session, with the Session header and no access token, and uses it only in that Session. Once a Session has read it, the Inspector lists the tasks under "Tasks not offered", each with the words of its alternative; before that, the Company profile's "Task coverage" row says where they are read. The Companies serve the same response to everyone, so they don't verify the header there and let it be cached. The response also names `feedback.endpoint`, where every Company takes reports (see Feedback under [Closed gaps](#closed-gaps-25-november-2026)), and carries a `skill_index`.
- Skills (§9.4): each Company publishes one or two in its tasks response's `skill_index`, in the format of the Agent Skills discovery proposal the spec pins (`$schema` `https://schemas.agentskills.io/discovery/0.2.0/schema.json`). Juniper has `move-recurring-delivery` and `open-support-case`, Lantern `change-scheduled-order`, Harborline `pay-saved-recipient`, Northwind `add-checked-bags` and `accept-upgrade-offer`, and Fernwick `switch-rate-plan`. A skill is one `SKILL.md` (type `skill-md`): the permissions the task needs, the order of calls by `operationId`, that the change comes back as a proposal the customer approves in their agent, and what the common outcomes mean. The gateway serves it at `/poppy/skills/{name}/SKILL.md` on the Company's origin as `text/markdown`, to `GET` and `HEAD`, with no Session header, cached like the tasks response. An entry's `url` is that path, which resolves against `tasks.endpoint` to the same file, and its `digest` is the SHA-256 of the bytes served, computed when the Company starts. Every Session gets the same index. Iris reads the index with the tasks and keeps the entries it can use: a known `$schema` and `type`, a well-formed digest, and a `url` that is HTTPS once resolved, on any host. The Inspector's Company profile lists them under "Skills published": each name, linked to its file, the description and the host that serves it, as text. Iris doesn't load a skill yet: it fetches no file, checks no digest, and gives the model neither the index nor a skill's contents.

## Sign-in (§4)

- **`prompt=consent`** on every Direct Sign-In, since the redirect can come back on another device. The Companies always show consent with every requested scope anyway.
- **Pushed Authorization Requests** (RFC 9126). The Companies offer `/oauth/par` (`require_pushed_authorization_requests: false`). Iris uses it whenever offered: it pushes the request with its client assertion and a DPoP proof, so the code is bound to that key, then opens the authorization endpoint with only `client_id` and `request_uri`. A `request_uri` lasts 90 seconds and makes one consent page: the browser that holds that page's cookie can reload it until it is answered, and nothing else can use the `request_uri` again.
- **Device Sign-In** (§4.3, RFC 8628). Juniper, Lantern, Northwind and Fernwick list `device_authorization_endpoint` (`/oauth/device`) and `urn:ietf:params:oauth:grant-type:device_code` in `grant_types_supported`. A request carries the client assertion and `scope`; it answers an eight-letter `user_code` such as `WDJB-MJHT` (consonants only, RFC 8628 §6.1), `verification_uri` `/device` on the Company's own origin, `verification_uri_complete` with the code in it, `expires_in` 600 and `interval` 5, and keeps only the hash of the `device_code`. Opening `/device`, with or without the code, changes nothing: the customer enters or confirms the code, then gets the consent sheet every time, with the notice described in [Permission consent](permission-consent.md#the-consent-page). Polls carry the client assertion and a DPoP proof, and get `authorization_pending`, `slow_down` (a poll more than a second early adds five seconds to the interval), `access_denied`, `expired_token`, or the tokens, once. The tokens are bound to the key of a DPoP proof sent with the request, or else to the first poll's key; refresh, DPoP and the approving browser's link to the visitor's copy (`isolation: "visitor"`) then work as after Direct Sign-In. Wrong codes are limited: ten in ten minutes from one address (Cloudflare's `CF-Connecting-IP`, taken only on Workers, where Cloudflare sets it, an IPv6 address counted by its /64; else the browser's cookie) or 1,000 in a minute from everyone stop code checks for a while (429). A wrong demo password on the consent page (`passwordHash`), here and in Direct Sign-In, is limited the same way: ten in a minute from one address (else that consent page) or 100 from everyone. The code form takes posts only from its own origin, and a browser joined to a Session can't use it (§6). A code entered in a second browser moves the consent page there, and the first one's answer is refused. Iris doesn't use Device Sign-In yet; `pap-client` has it (`startDeviceSignIn`, `pollDeviceSignIn`, `waitForDeviceSignIn` in `packages/pap-client/src/device-sign-in.ts`), checks the link's host before anything is shown (`deviceLinkAllowed`) and keeps the `device_code` out of what is shown.
- **Algorithms:** the Companies accept client assertions and delegations signed with `ES256` or `PS384` (RSA keys of 2048 to 4096 bits). The key's type chooses the algorithm; nothing in the JWT can.
- **Assertion lifetime:** at most 5 minutes from `iat` to `exp`. The Companies used to refuse any assertion older than 65 seconds, which 1.0 forbids; now the lifetime decides.
- **Refresh with the same DPoP key:** the Companies bind each refresh token to the DPoP key it was issued with and refuse a refresh with another key (`invalid_grant`). Iris keeps the key until the User signs in again.
- **One sign-in for every resource:** a token request naming `resource` = the domain gets the default token, and one naming the Company's MCP server (`https://{domain}/mcp`) gets a token that works only there ([MCP at the Companies](mcp-company.md#tokens)); any other `resource` gets `invalid_target`.
- **Bearer tokens for the MCP server only (§4.5):** a token request for the MCP server without a DPoP proof gets `token_type: "Bearer"`, and its grant gets Bearer tokens for the server at refresh. Every other token request still needs a proof: a refresh of that grant with a proof for the domain gets a DPoP-bound token, and binds the grant to that key for every later refresh, the server's included. The server takes a Bearer token only with a Session header whose `ath` covers it (another token's `ath` gets `invalid_session`, as any failed Session check), and each such Session JWT once; everywhere else it gets `invalid_token`.

## Sessions (§5)

- The Session JWT is unchanged from late 0.3: `poppy_dlg` carries a `poppy-delegation+jwt`. The earlier `pap_dlg` form, which Poppy Lab accepted during the 0.3 transition, is refused.
- A Session is named by `client_id`, `sid` **and User ID**: a known `sid` with another User ID is another Session, not an error.
- An ended Session gets **`session_ended`**, and so does a second account in one Session. Iris then starts a new Session and resends once. `invalid_session` is no longer retried, because a new Session would fail the same way.
- Sessions slide: each request keeps one going for another hour.

## Operations, version 3

- An operation has **required `terms`** and an optional `summary`. Iris shows the summary as text (Markdown, links and images never render), and when there is none it opens the exact terms.
- An approval says who approved it. On a click, Iris sends a user approval (`approver="user"`, `approved_at`, `input_type="tap"`, and a unique `reference` never shared across Companies). When a standing instruction matches—one per Company, checked against the exact server terms in deterministic code—Iris sends an agent approval (`approver="agent"` with a ledger `reference`). A retry after an unknown outcome sends the very same approval. At APIs it goes in `Poppy-Approval` (an RFC 9651 Dictionary); in a conversation, in `extensions.operations.approval`.
- The Companies record `approver` and `reference` with a performed operation and show who approved in their portals. They accept user and agent approvals; Harborline declines agent approvals that move money.
- **`approval_declined`:** Iris marks the card "Declined by the Company", shows the reason as Company content, and never sends that approval again.
- Not implemented: operations on websites.

## Conversations (§8)

See [conversations](conversations.md). In short: every `POST` has a request `id`, a reused ID with another path or body gets `request_id_conflict`, and a `POST` without `wait` returns only `conversation_id`. State is four fields: `working`, `handoff`, `responder` and `closed`. A handoff can be withdrawn at `handoff/cancel`, and a close returns 202. A read with `Accept: text/event-stream` gets the events as server-sent events, then each new one (§8.6), with no `text-delta`; Iris reads JSON.

## MCP (§7)

Every Company lists an MCP server at `https://{domain}/mcp` in `apis`, after its OpenAPI description, and in its issuer's `protected_resources`, with RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp`. The gateway serves it for all five (Streamable HTTP, MCP 2025-06-18): one tool per OpenAPI operation, each call the operation's own request to the same route, after the API's checks of the Session header, the token (one requested with `resource` set to the server's URL, and used only there: DPoP-bound, or a Bearer token bound by the Session header's `ath`), the route's extension, its scopes and Operations v3. A proposal returns the same operation as a tool error with `operation` in `structuredContent`, and the approval comes back in `_meta`. Details in [MCP at the Companies](mcp-company.md). Iris prefers OpenAPI, so it doesn't use these servers.

## Web browsing (§6)

Every Company lists `web.browser_session_endpoint`, `/poppy/browser-session` on its own origin, and the gateway serves the three steps of a browser join there (`packages/pap-company/src/gateway/browser-session.ts`). A join can be signed out or signed in. Either way the joined browser changes nothing on the website, and signed in it sees what the token's read scopes cover. No Company sets `web.unscoped`: the websites apply the scopes.

- **The page (step 1).** A GET returns a small page of the gateway's own, without script: a form that posts to the endpoint with the one-time code in a hidden `code` field, and a Continue button. The response sets `__Host-poppy_join` (`Path=/; Max-Age=60; Secure; HttpOnly; SameSite=Strict`) and carries `Cache-Control: no-store`, a `Content-Security-Policy` with `frame-ancestors 'none'`, and `Cross-Origin-Opener-Policy: same-origin`. It sets no other cookie and touches no Session. A page load keeps nothing on the server: the code holds when it ends, a minute later, and a keyed hash only the Company can make, and the join cookie is a keyed hash of the code.
- **Authorizing (step 2).** `POST /poppy/browser-session/authorize` with `{"code": …}` and the Session header, checked as at the APIs, answers 204. The Company then keeps the code, by its hash, for that Session until the code's minute ends. With an access token, checked as at the APIs too (the DPoP proof, one account per Session, the grant's agent user), the code is authorized for the token's account and scopes: the Company keeps those and the grant's key, never the token. The token needs `poppy:browser-sign-in`; without it the answer is 403 `insufficient_scope` with `WWW-Authenticate: DPoP error="insufficient_scope", scope="poppy:browser-sign-in"`, and the agent can authorize the same code again without the token. A code it didn't issue, an expired one, and one that was authorized or submitted before get 400 `invalid_request`; a missing or bad Session header gets 400 `invalid_session`. One agent user can have ten codes waiting and one agent a hundred; past that the answer is 429.
- **The form (step 3).** The first request that submits a code uses it, whatever the result. The browser gets the Session's cookie and a `303` to `/` only when it sends the join cookie of the page that held the code, the code was authorized, and its Session is still going. Anything else gets an error page with 400, or 429 over the bounds, and no cookie.
- **The Session's cookie.** `__Host-poppy_session` (`Path=/; Secure; HttpOnly; SameSite=Lax`), kept by its hash and looked up on every request. Its `Max-Age` is what the Session had left at the join, an hour at most, and the browser's own requests don't keep the Session going, so the cookie never outlives the Session. The agent joins again when the website stops recognizing it, and a new join replaces the cookie. On a local HTTP origin both cookies lose the `__Host-` prefix and `Secure`, like the gateway's other cookies.
- **The scope.** The gateway adds `poppy:browser-sign-in` to every Company's `scopes_supported`, and each Company describes it in `auth.scopes` with the hints `changes: none`, `personal_data: true`: it shows personal data and changes nothing. A consent grants it only when the agent asked for it and the customer left its own line allowed: "On this website: Browse signed in, read only", ticked when the page opens (`browserAccess` in `packages/pap-core/src/consent-sheet.ts`, the form field `allow_browser`). A Company's `selectScopes` never sees it. Iris never asks for it.
- **Signed in.** A browser joined with such a token is signed in to the token's account on `/account` and `/site/*`, in place of any login it had: the gateway ends the browser's own website logins where they were made and clears their cookies, and they don't come back (§6). The website shows each part of the account page with the read scope that covers the same data in the Company's API, and only the accounts or meters the grant shares; a part without its scope is left out, and the page names it with the scope to ask for. The connected agents, their activity and their reports are the customer's own: an agent's browser never sees them. Each Company's doc has its table.
- **How the sign-in ends.** The cookie acts for the account only while the grant of the token it was authorized with is there. The agent's revocation of its refresh token, which is how it signs out, Disconnect on the Company's website, and the grant's own end each take the grant away, and the browser is signed out on its next request, still a browser of the Session. The Session's end, an hour without a request from the agent, ends the join altogether. A join again without a token signs the browser out. A second account in the same Session gets `session_ended` at step 2 (§5.4).
- **Read only.** A joined browser, signed in or not, changes nothing. The Companies' APIs answer a change with a proposal the customer approves in their agent; the websites have no such step, because operations on websites aren't implemented. So the gateway refuses every request from a joined browser that isn't a read, before any route sees it and whatever the route, with 403: `{"error": "read_only_browser"}` and a description as JSON, or a page that says the same when the browser asks for HTML ("This browser belongs to an agent's session, so it can't change anything at Lantern Noodle Bar. Changes are made through the agent and wait for your approval there. Nothing has changed."). That covers every form and route of every website, the websites' own login and log out, Disconnect, and the consent page, so a joined browser can't allow its own agent. Three kinds of request are left to their own checks, because a cookie opens nothing at them: the join's own form, the Session destinations (the APIs, conversations, feedback, the authorization), which take a verified Session header, and the token, PAR and revocation endpoints. The websites render no control for a joined browser: no editor, no form, no Disconnect, no log out, no login form.
- **Who allows a consent.** The refusal above stops only a browser the gateway knows to be the agent's, one joined to a Session. A browser the agent drives without joining it is an ordinary visitor, and the lab's consent page asks for nothing the agent can't supply: it lists the test customers, and no password is needed unless the deployment sets the shared demo password (`passwordHash`), which the public Workers don't. So an agent with its own browser can open the authorization URL it made, choose a test customer and allow itself. It gets that customer only in a copy of the Company that belongs to one of its own users (`isolation: "visitor"` keeps a copy per agent user), never in a copy of another agent's users. The lab can't close this and keep its logins without a password: only something the customer has and the agent doesn't, such as a password, would tell the two browsers apart. A real Company signs the customer in on its consent page with credentials the agent never sees, such as a password, a passkey or an account with another provider (§4.2). That sign-in, not the refusal of joined browsers, is what keeps an agent from allowing itself, and it is why an agent must not hold the customer's credentials (§10.5).
- **Signed out.** A join without a token leaves a login the browser has as it is. With one copy for everyone (local development) the browser's own login still shows its account, read only. Where every agent user has its own copy of a Company (the public Workers), the joined browser sees the copy of its Session's agent user while the cookie works, and what it saw before once it stops; a login it made in another copy stays there and is not taken along, so on the Session's copy it is signed out. The websites log a customer in without a password, so taking a login along would show an agent's browser an account no scope covers. A browser that follows another agent user's copy, because it approved that agent's consent, sees the Session's copy while it is joined and the other one again afterwards.
- **Not done.** A joined browser can't sign out on the website (§6 lists that among the ways the sign-in ends; here the agent ends it). Operations on websites. Pages fetched without a browser don't have their Session header verified (§5.2). The FDX-shaped and ESPI-shaped scopes open little on Harborline's and Fernwick's account pages: the email at Harborline (`fdx:CUSTOMER_CONTACT`), the energy use and the service address at Fernwick (`espi:usage`, `espi:customer`). The pages' other parts go by each Company's own read scopes, as their docs say.
- **Iris doesn't browse**, so nothing in the playground uses the endpoint, and Iris never requests `poppy:browser-sign-in` (`consentScopes` in `packages/pap-agent/src/account-permissions.ts`). The Company profile lists the scope with a note that says so.

## Not yet done

Streaming, browsing in Iris, operations on websites, Device Sign-In in Iris (four of the Companies offer it), Mediated Sign-In, signed-in MCP and approvals over MCP `_meta` in Iris (the Companies' MCP servers take both), loading a Company's skills (Iris lists them and stops there), and Agent IDs.

## Closed gaps (25 November 2026)

- **Per-service tokens (§4.5).** Before its first signed-in call to an API or conversation endpoint, Iris reads that service's protected resource metadata (RFC 9728 §3.1) and uses it only if its `resource` is the service URL. A `resource` other than the domain's gets its own token from the refresh token, with `resource` and the same DPoP key; `invalid_target` means the service is used signed out. Our Companies' APIs and conversations take the default token; only their MCP servers need their own, and Iris doesn't use those signed in.
- **Choosing again (§3.4).** After `version_unsupported`, Iris fetches `poppy.json` again without a cached copy. If the chosen version changed, it starts a new Session and resends once; otherwise it stops.
- **The domain with the name (§10.3).** Discovery proves which domain published the document, not who owns it, so the approval card and the Company profile show the domain next to the name.
- **Feedback (§9.3).** Every Company lists `feedback.endpoint` in its tasks response and takes `{task, description}` reports with the Session header and no scope. It answers 202, or 200 with an alternative its own code matched: Lantern sends gift card and catering requests to its phone line, and Juniper sends gift cards and business accounts to its phone line and help page. Juniper answers every other valid report with an alternative too, never 202: what its interfaces can't do can be asked of its staff in a support case, with an `openapi` reference to `propose_support_case` in the API its `poppy.json` lists, which opens the case once the customer approves it. The other Companies have no such operation, so a report they don't match gets 202. Reports are data: no model reads them, and they stay in the reporting visitor's tenant. Iris offers `report_unsupported_task` when a Company takes feedback, sends each task once per Session (with the access token when signed in, which ties the report to the account), skips excluded tasks, and doesn't send a report that contains an email, phone number or ID. An alternative the Company answers with shows in the chat as its own entry, labelled Company content, with its references under "Data", so a model's answer doesn't have to put it in Iris's words; the model is told to quote what it passes on and say whose it is. The keyless demo sends a fixed report when you mention a gift card, and its answer says "Feedback report sent to the Company (§9.3)"; a report Iris held back, such as the same one again in that Session, is answered "Feedback report not sent to the Company (§9.3)" with the reason. The Inspector labels the request §9.3. Each Company's customer portal (`/account`) lists the reports in that visitor's copy under "Feedback from agents": the task, the description (escaped), the agent's host, the time and whether the Company offered an alternative. The portal shows the agent user's copy to the browser that approved the agent's consent, from the agent's first signed-in request on. Until then that browser sees its own copy, where the list of Connected agents already has the grant it approved, not yet used.
- **Operator signatures (§5.3).** Every request with the Session header also carries a Web Bot Auth signature (RFC 9421, `draft-ietf-webbotauth-httpsig-protocol-01`): `Signature-Agent` in its dictionary form, covering `@authority`, `@method`, `@path`, the `Signature-Agent` member, `poppy-session` and, when signed in, `authorization`, with `created`, `expires` (5 minutes), `keyid` (the JWK thumbprint), `alg="ed25519"`, a `nonce` and `tag="web-bot-auth"`. The Ed25519 key is derived from the identity secret (HKDF), apart from the `jwks_uri` and delegated keys, and published at `/.well-known/http-message-signatures-directory` with a possession signature over `@authority` and `Content-Digest`. The signer reproduces the RFC 9421 Ed25519 test vector byte for byte. The Companies don't verify it; the spec doesn't require them to.
