# OpenAPI-generated tools and approval presentation

The runtime now generates Juniper’s account tools from its actual `/openapi.json`. It no longer defines a separate per-endpoint shopping tool list. Changes to supported operation IDs, parameters and schemas are discovered on the next chat connection. The no-LLM demo still has an explicitly Juniper-specific natural-language router; this is not generic model reasoning.

## Supported subset

`packages/pap-client/src/openapi.ts` supports:

- Up to 24 uniquely named GET/proposal POST tools, scanning at most 64 paths.
- Scalar string/number/integer/boolean path and query parameters, with percent encoding and bound path placeholders.
- Bounded object/array JSON request bodies, explicit properties/required fields, no undeclared keys, a depth limit of four and a maximum of twenty array items.
- Enums, calendar-valid date strings and numeric/string bounds; runtime validation before any request, not just model-side JSON schemas.
- Same-origin absolute OpenAPI servers. Public GET discovery can work beyond the examples; account sign-in is limited to the exact configured example-Company origins and the three Sandbox examples.

Request-schema refs, compositions, multipart input, header/cookie parameters, parameter serialization variants, relative servers and per-operation server overrides are intentionally unsupported. Unsupported operations are omitted with sanitized Inspector trace entries. Duplicate operation IDs are removed rather than allowed to replace an existing tool. Schema strings and payload sizes are bounded. This is a conservative subset, not full OpenAPI conformance.

## FDX-shaped APIs: a native adapter

`packages/pap-client/src/fdx.ts` builds seven read tools for the `poppylab.dev/fdx` v1 extension instead of passing an FDX-shaped OpenAPI description through `openapi.ts`. The adapter is FDX-shaped, not FDX-conformant: it uses a hand-picked set of FDX resource paths and field names, and its descriptions are our own. No FDX text or schema is in the repository, because the FDX licence forbids copying it. The extension is described in [`poppylab.dev/fdx` v1](extensions/fdx.md).

The generic adapter isn't a good fit for two reasons:

- **Limits.** `openapi.ts` stops at 24 tools and 64 paths. A full FDX-style description has far more operations, so the generic adapter would keep an arbitrary first slice of them.
- **`$ref`.** FDX-style schemas are built from shared `$ref` components, which `openapi.ts` deliberately doesn't follow (it resolves only one level of `#/components/parameters`). It doesn't validate responses either, and FDX responses carry personal data from a Company.

| Tool                    | Request (under the entry's URLs)                                                             | Scopes                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `fdx_list_accounts`     | `GET {base_url}/accounts`                                                                    | `fdx:ACCOUNT_BASIC`, plus `fdx:ACCOUNT_DETAILED` with `balances` |
| `fdx_get_account`       | `GET {base_url}/accounts/{accountId}`                                                        | The same                                                         |
| `fdx_list_transactions` | `GET {base_url}/accounts/{accountId}/transactions?startTime&endTime&offset&limit`, paginated | `fdx:TRANSACTIONS`                                               |
| `fdx_list_statements`   | `GET {base_url}/accounts/{accountId}/statements?startTime&endTime&offset&limit`, paginated   | `fdx:STATEMENTS`                                                 |
| `fdx_get_statement`     | `GET {base_url}/accounts/{accountId}/statements/{statementId}`, `Accept: application/pdf`    | `fdx:STATEMENTS`                                                 |
| `fdx_get_customer`      | `GET {base_url}/customers/current`                                                           | `fdx:CUSTOMER_CONTACT`                                           |
| `fdx_consent_status`    | `GET {consent_endpoint}/{consentId}`                                                         | None (the grant's own token)                                     |

- **Input.** Closed schemas checked by the same code as `openapi.ts` (`boundedToolInput`), before any request. Ids are printable ASCII without `/`, `\`, `%`, `?` or `#`, at most 128 characters, and go percent-encoded into one path segment. Dates are calendar-valid `YYYY-MM-DD`, with the start no later than the end. Model input never supplies a URL, header, token or paging offset.
- **URLs.** Only from the entry that discovery validated against the Company's origin (§3, §3.3). The adapter refuses an entry whose two URLs are on different origins or carry credentials, a query or a fragment.
- **Paging.** Transactions and statements follow `page.nextOffset`, a decimal string (or a non-negative integer) that is absent on the last page. They read 50 per page, for at most 4 pages and 100 transactions or 50 statements per call, and stop on a repeated or malformed offset. The first page's `page.totalElements` is passed on, and `truncated: true` tells the model to narrow the dates.
- **Responses** are Company content (§10.1). The expected shapes: `{ accounts: [...], note }` for the list, `{ ...account, note }` for one account, `{ transactions: [...], page, note }`, `{ statements: [...], page, note }` with `statementId`, `accountId`, `statementDate`, `description`, `status` and, when present, Harborline's own `startDate` and `endDate` (a statement for another account is dropped), `{ customerId, name: { first, middle?, last }, email: [...], note }`, and a consent with `parties` as `{ name, type }`. `accountNumberDisplay` is the last four digits, and `note` is Harborline's fiction notice. Each response is reduced to the fields the adapter knows, with bounded strings (control and line-separator characters replaced) and at most 50 accounts. Balances are kept only when the call asked for them. A response for another account or consent than the one asked for is `invalid_response`.
- **Documents.** A model can't read a PDF, and a statement is Company content (§10.1), so `fdx_get_statement` never returns its bytes. It asks the transport for a document (`accept: "application/pdf"`, `maxBytes` 512,000) and checks the answer: a 2xx with content type `application/pdf` (parameters allowed), at least 16 bytes and at most the cap, starting with `%PDF-`. The model then gets `{ statementId, accountId, contentType, bytes, sha256 }` and a description that points it to `fdx_list_transactions` for the statement's dates; anything else is `invalid_response`. `fdxStatementPdf` makes the same request and checks for a caller that hands the file to the User.
- **Errors.** An FDX error body (`code`, `message`, `debugMessage`) comes back as `{ error: "fdx_error", status, code, message, debugMessage }`, each bounded; any other error body is reduced to its status.
- **Transport.** The caller injects `request(url, scopes, options?)`. It adds the Session header, DPoP and the token, and returns the status and parsed body, or an outcome of its own, such as "sign in first", which goes to the model as it is. With `options` (`{ accept, maxBytes }`) a success comes back as a document instead, `{ status, contentType, bytes }`, unparsed; errors still come as a parsed body. `protocolRequest` has a matching `binary: { maxBytes }` option, and its default `Accept: application/json` gives way to the caller's.
- **Consent id.** A caller that keeps the `consent_id` from its token response passes `consentId: () => id`. `fdx_consent_status` then takes no id from the model. Without one it answers `consent_unknown` and sends nothing.

### In the playground: Use FDX and Use ESPI

The account row has one control for a Company's domain extension: **Use FDX** where the profile has a valid `poppylab.dev/fdx` v1 entry (Harborline), **Use ESPI** where it has a valid `poppylab.dev/espi` v1 entry (Fernwick). Both are the same code: `packages/pap-agent/src/domain-extension.ts` lists the two extensions (the connection's flag, label, shape, scope prefix and, for ESPI, the scopes its tools use), and the runtime, the account route and the page read that list. A run keeps the choice in its connection to the Company, as `fdx` or `espi`; runs saved with `run.fdx`, before a run had connections, are read into one and work as before. The rest of this section describes Use FDX; [Use ESPI](#use-espi) says what differs.

Iris uses the FDX-shaped tools only when the User turns on **Use FDX** in the Company's account row. The control appears for a Company whose profile has a valid `poppylab.dev/fdx` v1 entry, which today means Harborline only. It is off in every new conversation and saved with the run, in its connection to the Company.

- **Declaration.** With Use FDX on, every request in the Session sends `Poppy-Extensions: "operations";v="3", "poppylab.dev/fdx";v="1"` (`declaredExtensions` in `packages/pap-agent/src/session.ts`). With it off, only `"operations";v="3"` is sent, and Harborline answers `403 extension_required` on `/fdx/`. Declarations are fixed for a Session (§3.4), so switching Use FDX on or off starts a new Session. Sign-in is kept.
- **Which description goes where.** The generic adapter still gets the Company's own API: the first OpenAPI entry, or MCP when there is none. An entry is treated as the FDX-shaped API, and skipped with an Inspector line, when its URL is under `base_url`, its first server is at or under `base_url`, or every path it describes resolves under `base_url`. The URL alone isn't enough, because Harborline serves the description at `/openapi/fdx.json`, outside `base_url`, with its origin as the server and `/fdx/v6/...` paths. The generic adapter also blocks the `base_url` and `consent_endpoint` paths, so an FDX-shaped route never becomes a generic tool, whether or not Use FDX is on. The Inspector shows `Extension poppylab.dev/fdx v1 · native FDX-shaped adapter · 7 read tools`.
- **Steering.** With Use FDX on, the description of `fdx_list_accounts` starts with one sentence (`FDX_GUIDANCE` in `packages/pap-agent/src/fdx-runtime.ts`): for accounts, balances, transactions and statements, use the `fdx_` tools rather than the Company's own API tools. It's a preference, not a block. The Company's own API tools stay offered, and Harborline applies the accounts chosen at consent to both APIs ([The account choice](harborline-bank.md#the-account-choice)).
- **Transport.** Requests go through `papRequest`, as for any API tool. They carry the Session header, the operator signature and DPoP, and they follow the same SSRF, redirect and `session_ended` rules. `fdx_consent_status` declares no scope but still sends the access token. `protocolRequest` has an opt-in `errorBody` option: a `ProtocolError` then keeps the parsed body, but only for an error that has no known Poppy or OAuth `error` code and no `WWW-Authenticate` header. The FDX transport passes those 4xx bodies (other than 429) to the adapter as `{ status, body }`, so `701`, `703`, `invalid_parameter` and `consent_not_found` reach the model as `fdx_error`. Everything else is thrown as before: `extension_required`, `invalid_session`, `session_ended`, `version_unsupported`, `insufficient_scope`, token errors (including Harborline's `401 602`, which comes with `WWW-Authenticate: DPoP error="invalid_token"`), 429 and 5xx.
- **Statements.** A statement is read as a document through `papRequest`'s `binary` option: `Accept: application/pdf` and a 512,000-byte cap, with the same Session header, DPoP token, SSRF, redirect and `session_ended` rules; its error bodies reach the adapter as above. Signed in with Use FDX on and `fdx:STATEMENTS` granted, the account row offers **Show FDX statements** (`{ "action": "fdx_statements" }` on `/api/account`). The route reads them through the adapter's `fdx_list_accounts` and `fdx_list_statements`, as the model would, and returns only each account's id, name, last four digits and its statements' ids, dates and descriptions. Each statement has **Download PDF**, which sends `{ "action": "fdx_statement", accountId, statementId }`. The route checks both ids with the adapter's id rule (`validFdxId`) before anything is sent, and `fdxStatementDownload` in `packages/pap-agent/src/fdx-runtime.ts` builds `GET {base_url}/accounts/{accountId}/statements/{statementId}` from the validated entry only, never from the page. The adapter's checks pass, so the route answers the PDF with `Content-Type: application/pdf`, `Content-Disposition: attachment; filename="statement-{accountId}-{statementId}.pdf"` (characters other than letters, digits, `.`, `_` and `-` replaced), `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and the SHA-256 in `X-Poppy-Statement-Sha256`. The page saves it as a file with a temporary link, with no browser dialog, and logs its size in the Inspector. Refusals are in our own words: `400 no_fdx_access` signed out or with Use FDX off, `400 invalid_request` for an id the rule refuses, `401 account_unavailable` for access already refused, `403 insufficient_scope` without `fdx:STATEMENTS`, `404 statement_not_found` for the bank's 404 (an unknown statement or an unshared account's `701`), and `502 fdx_statement_failed` for anything that isn't a bounded PDF. The model never gets the bytes.
- **Scopes.** The `fdx:` data clusters are requested only with Use FDX on. Then the read sign-in asks for them alongside the Company's other read-only scopes (RFC 9700 §2.3, as fine-grained as the read/write choice allows). Signed out, a tool answers `sign_in_required`. When the grant lacks a cluster the call needs, the tool answers `insufficient_scope` with the missing clusters, sends nothing, and the account row offers **Sign in again to share accounts over FDX**.
- **Consent id.** The `consent_id` of a token response (sign-in and refresh) is kept in the connection, and dropped at sign-out or by a sign-in without one. `fdx_consent_status` uses it when the model names none (`fdxTools({ consentId })`), so the model never has to know or invent it.
- **Revoking the consent.** Signed in with Use FDX on and a consent id known, the account row shows the consent: its id, then its status, shared accounts and expiry, read once through `fdx_consent_status` (`{ "action": "fdx_consent" }` on `/api/account`). **Revoke FDX consent** asks again in the page (**Confirm revoke** or **Cancel**, no browser dialog) and then sends `{ "action": "fdx_revoke" }`. The route takes no URL or id from the page: `revokeFdxConsent` in `packages/pap-agent/src/fdx-runtime.ts` builds `PUT {consent_endpoint}/{consent id}/revocation` from the validated entry and the stored id and sends `{ "reason": "USER_ACTION", "initiator": "INDIVIDUAL" }` through `papRequest`, with the Session header, DPoP token, `Poppy-Extensions` and the usual SSRF and redirect rules. It answers `400 no_fdx_consent`, sending nothing, when signed out, with Use FDX off or without a consent id, and `401 account_unavailable` when the Company already refused this access.
  - **`204`.** The grant and its access and refresh tokens are gone at the Company. The connection is signed out as after a sign-out (tokens, scopes, consent id, per-service tokens and the account conversation cleared; the run and the Company's Session kept), without revoking the dead refresh token again. The route answers `{ signedIn: false, revoked: "revoked", consent }`, the page says the consent was revoked and offers sign-in again, and the Inspector logs `PUT /fdx/v6/consents/{id}/revocation · FDX consent revoked · 204`.
  - **`401`** (`invalid_token`, or a refresh answered `invalid_grant`). The consent had already ended: the connection is signed out the same way, and the route answers `revoked: "already_ended"`.
  - **Anything else** (a `4xx`, `5xx`, `429` or no answer). The sign-in is kept; the route answers `502 fdx_revoke_failed` with a message, and the Inspector logs `FDX consent revocation failed`.
  - It is the User's action: no model tool revokes, like sign-in and sign-out.
- **Demo mode** (no model) runs its scripted examples only ([Demo mode](chat-workspace.md#demo-mode)). With Use FDX on, "my account balances" and "my recent transactions" (the rules in `packages/pap-agent/src/demo-fdx.ts` also take `saldo`, `movimientos`, `statements` and `extractos`, for when they are examples) read through `fdx_list_accounts` and `fdx_list_transactions` or `fdx_list_statements` (`packages/pap-agent/src/demo-fdx.ts`). The answer names each shared account by product name and last four digits, with amounts in the account's currency and debits signed, or each statement's date, description and status; for statements it says the PDFs download from the account row. "Data" keeps the exact FDX-shaped JSON.

`lib/fdx-runtime.test.ts` checks this with a fake transport, including the statement document's `Accept`, cap and checks and `fdxStatementDownload`'s refusals. `app/api/account/route.test.ts` checks the consent actions (refusals, the one `PUT` with its body and headers, `204`, `401` and other failures) and the statement actions (refusals sending nothing, one `GET` built from the entry with the body's URL ignored, the response headers and our own file name, `404`, non-PDF answers and a missing cluster). `app/playground/fdx-statements.test.ts` renders the statements in the account row. `lib/fdx-harborline.test.ts` runs the playground's routes and runtime against the real Harborline app in process, with only DNS and the pinned fetch replaced. It covers discovery, sign-in sharing one of two accounts, balances with and without `fdx:ACCOUNT_DETAILED`, paging, `701`, consent status, statements (listed, checked by the tool, listed in the account row and downloaded as the same PDF the tool hashed, with the unshared account's refused), demo-mode chats, `extension_required` with Use FDX off, revocation from the account row (one `PUT`, the old access and refresh tokens refused afterwards, the connection signed out, a new consent at the next sign-in), and a consent revoked by another request. `app/playground/fdx-consent.test.ts` renders the consent and both steps of its confirmation.

#### Use ESPI

At Fernwick the same control reads **Use ESPI**, with the ESPI-shaped tools of the next section. It is off in every new conversation and saved with the run, in its connection (`espi`).

- **Declaration.** With Use ESPI on, every request in the Session sends `Poppy-Extensions: "operations";v="3", "poppylab.dev/espi";v="1"`; off, only Operations, and Fernwick answers `403 extension_required` under `/espi/`. Switching it starts a new Session and keeps the sign-in. The Inspector shows `Extension poppylab.dev/espi v1 · native ESPI-shaped adapter · 4 read tools`. Fernwick's own API stays with the generic adapter, which also blocks the `resource_endpoint` path.
- **Steering.** The description of `espi_meters` starts with `ESPI_GUIDANCE` (`packages/pap-agent/src/espi-runtime.ts`): for electricity usage, costs and bills, use the `espi_` tools rather than the Company's own API tools. A preference, not a block; Fernwick applies the meters chosen at consent to both APIs.
- **Scopes.** With Use ESPI on, the sign-in also asks for the ESPI-shaped scopes the tools use, `espi:usage` and `espi:summary`, never `espi:customer`, which no tool uses. Signed out, every tool answers `sign_in_required` and sends nothing; a missing scope is `insufficient_scope`, and the row offers **Sign in again to share meters over ESPI**.
- **Transport.** Every request goes through `papRequest` with `binary`: `Accept: application/atom+xml` and the adapter's 1,000,000-byte cap, with the Session header, operator signature, DPoP token, SSRF, redirect and `session_ended` rules of any API tool. An error body that is the API's own (`invalid_parameter`) reaches the adapter as for FDX. So does Fernwick's bare `404`, which has no body: a `4xx` other than `401` and `429` with no known Poppy or OAuth code and no challenge goes to the adapter as `{ status, body: null }`, and the model gets `{ "error": "espi_error", "status": 404 }`. Protocol and token errors are thrown as before.
- **Subscription.** `resourceURI` and `authorizationURI` from the token response (sign-in and refresh) are kept in the connection as `espiResourceUri` and `espiAuthorizationUri`, only when they fit the entry exactly (`espiUri` in `packages/pap-agent/src/token-response.ts`): the endpoint's origin, no credentials, no query or fragment (an empty `?` or `#` included), written as the URL parser writes it, and exactly `{resource_endpoint}/Batch/Subscription/{id}` or `…/Authorization/{id}` with an id that passes the adapter's id rule and has no `%`. A sign-in replaces both, a refresh keeps those it doesn't repeat, and sign-out and revocation clear them.
- **Revoking.** Signed in with Use ESPI on and an authorization kept, the account row shows `ESPI authorization {id}`, then its status, shared meters and expiry, read once through `espi_authorization` and, with `espi:usage`, `espi_meters` (`{ "action": "espi_authorization" }` on `/api/account`). **Revoke ESPI access** asks again in the page and sends `{ "action": "espi_revoke" }`. `revokeEspiAuthorization` sends one `DELETE {authorizationURI}`, the kept URI checked again, through `papRequest`. It answers `400 no_espi_authorization`, sending nothing, when signed out, with Use ESPI off or without a URI that fits, and `401 account_unavailable` for access already refused. On `204` the connection is signed out as after a sign-out, without revoking the dead refresh token, and the route answers `{ signedIn: false, revoked: "revoked", authorization }` with `DELETE /espi/1_1/resource/Authorization/{id} · ESPI authorization revoked · 204` in its trace. On `401` it is signed out the same way (`revoked: "already_ended"`). Anything else keeps the sign-in and answers `502 espi_revoke_failed`. The FDX and ESPI revocations share the route's answer and the runtime's request code. No model tool revokes.
- **Demo mode** (no model) runs its scripted examples only ([Demo mode](chat-workspace.md#demo-mode)): "How much electricity did my EV use last week?" and "my bills" at Fernwick. With Use ESPI on, the rules read a message about usage, matched by word stem (`consum…` as in "consumo", "consumido" or "consumption", `electri…`, `eléctri…`, `energ…`, `kWh`, `usage`, `use`, `used`, `uso`, `luz`), reads each shared meter's last seven days through `espi_meters` and `espi_usage`; one about bills (`bill…`, `factur…`, `recibo…`, `invoice…`, and money paid: `pay…`, `paid`, `pag…` as in "pagué"), checked first, reads `espi_bills` (`packages/pap-agent/src/demo-espi.ts`). Spending (`gast…`, `spend`) is left out: "¿Cuánto gasté el mes pasado?" is as likely a bill as a week's energy, so it falls through to the Company's own API. The answer lists kWh and dollars per day, the total, the hours counted and the highest hour, or each bill's period, kWh, amount and tariff. "Data" keeps the exact tool output.

`lib/espi-runtime.test.ts` checks this with a fake transport: the declaration, the new Session, which tools exist and which is steered, the Atom request and its options, sign-in and scope answers, error passthrough and the errors thrown, URIs kept on refresh, and the `DELETE` and its refusals. `lib/token-response.test.ts` checks which URIs are kept. `app/api/account/route.test.ts` checks the toggle, the scopes asked for, sign-out, and the authorization actions (refusals sending nothing, one `DELETE` with its headers, `204`, `401`, other failures, the record with and without `espi:usage`). `lib/espi-fernwick.test.ts` checks the adapter against the real Fernwick: every day, hour and bill of a shared meter against Fernwick's own hourly readings and bills. `lib/use-espi-fernwick.test.ts` runs the playground's routes against Fernwick in process: Use ESPI on in a new Session, sign-in sharing one of two meters, the tools and their headers, the unshared meter's 404, demo chats, refresh, Use ESPI off and `extension_required`, revocation from the account row (one `DELETE`, the tools then answering `sign_in_required` and Fernwick `401` and `invalid_grant` for the old tokens, a new authorization at the next sign-in) and an authorization revoked by another request. `app/playground/espi-authorization.test.ts` renders the subscription and both steps of its confirmation.

## ESPI-shaped APIs: a native adapter

`packages/pap-client/src/espi.ts` builds four read tools for the `poppylab.dev/espi` v1 extension, the read-only usage API of an electricity utility. The API is ESPI-shaped (modelled on NAESB REQ.21 ESPI), not certified. Element names, codes and URL patterns follow the ESPI XML schemas, which are Apache-2.0. The descriptions, fixtures and data are our own, and no REQ.21 text is in the repository. The plan is [plan/espi-utility.md](../plan/espi-utility.md). The playground uses them with **Use ESPI** on ([Use ESPI](#use-espi)).

The generic adapter can't serve this API, for two reasons:

- **XML.** ESPI has no JSON. It serves Atom feeds (`application/atom+xml`) with ESPI elements inside `atom:content`, and `openapi.ts` and the transport read JSON only.
- **Volume.** A meter reports one interval an hour, which is 2,208 intervals per reading over the longest window of 92 days. The model can't take that many, so the adapter adds them up and returns days, hours, totals and bills. The model never sees a raw interval.

| Tool                 | Requests (under `resource_endpoint`)                                                                                                                                                                            | Scopes                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `espi_meters`        | `Subscription/{sub}/UsagePoint`, then `…/UsagePoint/{up}/MeterReading` for each usage point and `ReadingType/{id}` for each reading type                                                                        | `espi:usage`                                   |
| `espi_usage`         | `Subscription/{sub}/UsagePoint/{up}`, its `LocalTimeParameters/{id}`, `…/MeterReading`, `ReadingType/{id}`, then `…/MeterReading/{mr}/IntervalBlock?published-min&published-max&start-index&max-results`, paged | `espi:usage`                                   |
| `espi_bills`         | `Subscription/{sub}/UsagePoint/{up}`, its `LocalTimeParameters/{id}`, then `…/UsagePoint/{up}/UsageSummary?published-min&published-max&start-index&max-results`, paged                                          | `espi:summary`, for the meter and its time too |
| `espi_authorization` | The kept `authorizationURI`, `Authorization/{id}`                                                                                                                                                               | None (any token of the grant)                  |

- **What the model gets.** `espi_meters` lists each chosen usage point (`usagePointId`, title, service kind) with its meter readings. Each reading's ReadingType comes in words and in codes: direction (`consumption` for `flowDirection` 1, `export` for 19, `net`, `total`), quantity, unit with its power of ten, interval length, accumulation, commodity and currency. `espi_usage` takes `{ usagePointId, from, to, granularity }`, local dates both included, and answers for each meter reading with kWh and cost per day, or per hour for at most 3 days, and the total. It also gives the 5 hours of highest use and the number of days without data. A reading that isn't energy per interval in Wh (`uom` 72, `accumulationBehaviour` 4) is listed as skipped and isn't added up. `espi_bills` takes `{ usagePointId, from?, to? }`, by default the last 92 days. Each bill has its billing period as dates, both included: local dates, or UTC dates with `timeZone: "UTC"` for a period that starts at UTC midnight and not at local midnight (Fernwick bills UTC months, which in Pacific dates would seem to start the day before). Then kWh, amount, other charges with their line items, tariff and status time. `espi_authorization` gives the status (`active` for 1, `revoked` for 0, `denied` for 2), authorized and published periods, expiry, scope and subscription id. It never returns the `access_token` or `refresh_token` an Authorization may carry.
- **Decoding.** A value is Wh × 10^`powerOfTenMultiplier` (−12 to 12), shown in kWh to 3 decimals. Costs and amounts are hundred-thousandths of the currency (1234000 is 12.34) and are shown to 2 decimals. The currency is the ISO 4217 numeric code (840 is USD); with an unknown code, no cost is shown. Times are seconds since 1970 UTC. Days and hours are in the utility's local time, from `LocalTimeParameters`: `tzOffset`, `dstOffset` and the `dstStartRule` and `dstEndRule` bitmaps (bits 0–11 seconds, 12–16 hours, 17–19 weekday with Monday as 1, 20–24 day of the month, 25–27 operator, 28–31 month; `FFFFFFFF` means no DST). DST starts at the start rule's time in standard time and ends at the end rule's time in daylight time, as US clocks change. An end before the start means a southern-hemisphere year. An unreadable rule means no DST, and the answer says so; with no `LocalTimeParameters`, the answer says it used UTC. A local day can have 23 or 25 hours.
- **Window and paging.** `from` and `to` become `published-min` and `published-max` at local midnight (RFC 3339, UTC), with the end exclusive: at most 92 days, or 3 for hours, and `from` no later than `to`. Intervals outside the window, without a time period, beyond Int48, or repeating an hour already counted are dropped on our side as well. Interval blocks and summaries are read 31 entries at a time (`max-results`), from `start-index` 1, 32, 63 and so on. That is at most 4 pages per meter reading. Paging stops at a short page, and `truncated: true` says that a page bound was hit.
- **Bounds.** One call sends at most 32 requests. It reads at most 8 usage points, 4 meter readings per usage point, 10,000 intervals and 24 bills. Each feed is at most 1,000,000 bytes and is parsed with the XML limits below. Titles and notes are cut to 120 characters, with control and line-separator characters replaced.
- **Input.** Closed schemas checked by `boundedToolInput`, as for FDX, before any request. `usagePointId` follows the FDX id rule (`validFdxId`): printable ASCII without `/`, `\`, `%`, `?` or `#`, at most 128 characters, never `.` or `..`. It goes percent-encoded into its own path segment. Dates are calendar-valid `YYYY-MM-DD`. Model input never supplies a URL, header, token, subscription or paging parameter.
- **URLs and ids.** Requests are built only from the validated `resource_endpoint`. The adapter refuses an entry that carries credentials, a query or a fragment. The subscription comes from the `resourceURI` that the runtime kept from the token response. It has to be exactly `{resource_endpoint}/Batch/Subscription/{id}`, and `espi_authorization` reads only a kept `authorizationURI` that is exactly `{resource_endpoint}/Authorization/{id}`. Without such a URI, the tools answer `subscription_unknown` or `authorization_unknown` and send nothing. Links in a response are read back into ids only when they are under `resource_endpoint` on its origin, with no query, fragment or percent-encoding. An entry whose self link belongs to another subscription, usage point or meter reading is dropped. A ReadingType or LocalTimeParameters link that leaves the endpoint is never followed. An Authorization whose own `authorizationURI` or self link names another id is `invalid_response`.
- **Errors.** A 404 is `{ error: "espi_error", status: 404 }` with nothing more, because the utility doesn't reveal whether a resource exists. Another error with the lab's own JSON body `{ error, description }` comes back as `{ error: "espi_error", status, code, description }`, bounded; any other error body is reduced to its status. A success that isn't `application/atom+xml` or `application/xml` (UTF-8 if a charset is given) is `invalid_response`. So is one that is too big or that the parser refuses, and the trace then names the parser's reason.
- **Transport.** The caller injects `request(url, scopes, { accept: "application/atom+xml", maxBytes })`. A success comes back as a document, `{ status, contentType, bytes }`, unparsed. An error comes as `{ status, body }` with the parsed JSON body, or as an outcome of the caller's own, which goes to the model as it is. This is the FDX statement transport with another `Accept`: `protocolRequest`'s `binary: { maxBytes }` with an `Accept: application/atom+xml` header. The Session header, DPoP, SSRF, redirect and `session_ended` rules stay the same.

`espi.test.ts` runs every tool against `fixtures/espi-fernwick.xml`, a hand-written Batch feed for a fictional customer. It has a home meter and an EV charger meter, with three days of hourly intervals, their ReadingTypes, Pacific LocalTimeParameters, two monthly UsageSummary entries and the Authorization entry. The tests cover URL building, decoding (powers of ten, currencies, export, unknown codes), aggregation by local day and hour (including the 25-hour day when DST ends), clipping to the window, paging bounds, errors and refusals of cross-origin or foreign links and of a `resourceURI` or `authorizationURI` outside the endpoint.

### The XML parser

`packages/pap-client/src/xml.ts` is a strict, dependency-free XML 1.0 parser for the subset this Atom uses. It returns a small tree: for each element, its namespace URI, local name, attributes, children and text. It refuses anything outside the subset rather than skipping it:

- **No DTD.** `<!DOCTYPE` and every other `<!` declaration is refused, so no entity can be defined (billion laughs, external entities). Only the five predefined entities and numeric character references to characters XML allows are decoded. Any other reference, and a bare or unterminated `&`, is refused.
- **No processing instructions** except the XML declaration, which may only open the document, after an optional byte order mark. It must be version 1.0, and UTF-8 if it gives an encoding. Bytes are decoded as UTF-8, and invalid sequences are refused.
- **No CDATA sections.** ESPI content is numbers, codes and short text, so escaped character data is enough, and refusing CDATA keeps the parser smaller. A literal `]]>` in text is refused too.
- **Well-formed.** End tags must match, there is one root, and only whitespace and comments may appear around it. Comments can't contain `--`. Characters XML doesn't allow are refused, raw or as references, including lone surrogates. Line ends are normalized.
- **Attributes.** Values are quoted, with no `<`, and attributes are separated by whitespace. A duplicate attribute is refused, whether as written or once namespaces are resolved (`p:x` and `q:x` with the same URI). Unprefixed attributes are kept by local name and namespaced ones as `{uri}local`, in a record with no prototype.
- **Namespaces.** Every prefix used must be declared in scope; `xml` is built in. `xmlns:p=""`, declaring the `xmlns` prefix, binding `xml` to another URI or its URI to another prefix, and making either reserved URI the default are refused. A nested element may bind a prefix to another URI, as XML allows, and `xmlns=""` clears the default namespace.
- **Bounds** (`XML_LIMITS`, which a caller can tighten): at most 1,000,000 UTF-8 bytes, depth 32, 50,000 elements, 16 attributes per element, 2,048 characters per attribute value, names of 64 characters per part, and 4,096 characters of text per element. Whitespace-only runs between children don't count.
- **Errors** are `XmlError`, and the message never quotes the input.

`xml.test.ts` covers what the parser reads and, at greater length, what it refuses: billion laughs and external entity attempts, unknown entities, processing instructions, declarations in the wrong place, CDATA, mismatched and stray tags, unbalanced, duplicate or huge attributes, undeclared and reserved prefixes, namespace rebinding, BOMs, invalid UTF-8 and characters, malformed comments, and every bound, including nesting 100,000 deep.

## Authority boundary

The Poppy Lab Companies use two **local experimental OpenAPI annotations**, not standardized Poppy fields:

- `x-poppy-scopes` declares required account scopes for a tool.
- `x-poppy-proposal: true` plus a declared HTTP 202 response identifies an endpoint that only proposes an operation.

Metadata alone never authorizes POST. The runtime independently allows proposal POSTs only for the exact configured Juniper, Lantern, Harborline, Northwind and Fernwick origins and the three exact PAP Sandbox example origins; other Companies’ POST tools are omitted even if their schemas claim proposal support. The Sandbox’s singular scope annotation/DPoP security scopes and HTTP 202 Operations response declaration are also recognized. See pap-sandbox.md for that compatibility profile and public-identity setup. A trusted Company must actually enforce its proposal-only contract. Checking a response after an unsafe write would not undo it; the adapter is not a sandbox for arbitrary Company writes.

OAuth, agent/control endpoints, and Operations endpoints are excluded, including when hidden in the server base path. Model input cannot provide a destination URL, headers, token, approval mode or confirmation endpoint. Existing SSRF/DNS pinning, redirect refusal, DPoP and same-origin server policies still apply.

Poppy owns tokens/proofs and enforces declared account scopes before calling the Company; each Poppy Lab Company independently enforces scopes again. Proposal responses must have a valid ID, revision, state, summary, terms and expiry before entering the approval UI. Confirm, cancel, status recovery, sign-in and revocation remain outside the generated model tool set.

## Human approval

`operation-review.tsx` expands active proposals and collapses completed/declined/failed/expired records, each of which says on its closed entry how it ended (the Company's result as its own words and who approved, or why nothing was done). It shows Company identity, the exact Company summary, known before→after day/quantity changes, readable line items and formatted currency amounts. New basket/recurring proposals include Company-owned product names and prior quantities. Old saved records without a prior value say “Not provided” rather than inventing it. Terms it has no layout for are shown as rows read from their shape: field names as labels, `*_cents` as money, and paired fields (`from_x`/`to_x`, `x_before`/`x_after`) as one before→after change.

Complete structured terms remain available under **All exact terms**, without replacing Company truth with model-generated copy. Confirmation still covers the server-owned operation ID and exact revision. Expiry locally disables approval and preserves status recovery; Company expiry enforcement remains authoritative. No UI rendering or natural-language message confirms a proposal.

## Verification

Tests cover generated path/query/body tools, unknown/invalid input, cross-origin/control endpoints, server-base bypasses, unsupported schemas, duplicate IDs, tool limits, the actual Juniper and Northwind contracts, currency presentation, missing historical values, collapsed final states and expired approvals.

A real configured-model browser pass read the basket and invoked the generated basket proposal tool; another retrieved an order through its path ID. A no-LLM pass exercised the generated delivery-day proposal. Test proposals were declined without applying account changes. Desktop/mobile inspection showed open pending proposals, folded final results and no horizontal page overflow.

General cross-Company OAuth, all-schema OpenAPI support, arbitrary writes and public deployment remain out of scope.
