# Conversation continuity and viewport composer

## Conversations have addresses

Each conversation with a Company is one run, and its ID is the page's address: `/playground/<id>`. `/playground` is a new, empty conversation; connecting to a Company starts the run and puts its ID in the address. The ID is a name, not a key: the server looks it up under the visitor's cookie, so the address opens nothing in another browser (the page says so and offers a new conversation).

- **Running:** 30 minutes from its start, at most five at a time. Requests name it in the `X-Poppy-Conversation` header; the server answers with the same header, so a conversation that had to be started again (the old one ended) moves the address to the new ID. No cookie names a run any more.
- **Ended:** when it expires, is pushed out by a sixth, or the demo is reset, a conversation becomes read-only. Its tokens, keys, Session and pending sign-in are removed; the transcript, the Company and how its proposals ended stay. It is kept for seven days from its start, up to 20 conversations per visitor (the oldest ended ones go first). One in which nothing was said or signed in is dropped instead.
- **Transcript:** `history` is still cut to the model's last ten turns; `transcript` keeps the conversation for the page and resets wherever `history` does: sign-out empties it, and a sign-in, or the Company taking the access back, keeps only the entries shown while signed out (see [permission and consent](permission-consent.md)). It holds what the page showed, so a reload or the History view shows it again: the User's words (those said in a Direct Conversation marked as such), each Company content entry with its author, and each answer with its label, its "What Iris did" steps and its "Data". None of that goes into `history`: the model is sent a turn's words only, and never Company content or the User's direct words. How an approval ended is the other way round: `history` gets a line that tells the model, and the transcript gets none, because the page showed the outcome on the operation's entry and gets it again with the run's operations. The transcript is bounded (`TRANSCRIPT_LIMITS` in `lib/transcript.ts`): 200 entries, 12,000 characters of words and 20,000 of data per entry, 30 steps per answer, and 256 KB in all. Over that, the oldest data goes first, then the oldest steps, then the oldest entries. It holds no tokens, headers or request bodies.
- **Inspector lines:** the run also keeps the Inspector's "Session & API calls" lines (`log`, `lib/inspector-log.ts`), so a reload, the History view and an ended conversation list them again. Each kept line is a time and the words the Inspector showed, with any query string cut: no token, header, body or code. The chat and account routes keep the lines their answers carry, and the sign-in callback keeps its own line. Two lines the page writes itself are kept in the same words: "Applying your standing instruction", when the server's check agrees, and a statement download. "Standing instruction not applied" is written for every waiting change the instruction leaves to the User, with the reason its card gives: the terms aren't covered (over the limit, a refund, another currency), or the hour's allowance is used up. The instruction lives in the browser, so the page asks (`not_applied`); the account route makes the check again, writes the line in its own words and keeps it once for each reason, with the reason on the operation (`notApplied`), so a reload lists the line as it was and asks for nothing. Only which of the hour's two limits holds a covered change back is the page's word, since the page counts the hour over every conversation with the Company; when the run's own hour refuses an approval the page asked for, the route writes the line itself. The lines are bounded (`LOG_LIMITS`): 400 lines, 300 characters each and 64 KB in all, the oldest dropped first. The lines follow the conversation. A sign-in keeps only the lines written while no account was signed in, as the transcript does. Sign-out, and the revocation of an FDX consent or ESPI authorization, empty them with the transcript, what was written signed out included: the lines of that request are all that is listed afterwards, on the page and after a reload.
- **History view:** lists them (`GET /api/conversations`: names and times only) and links to each address. A conversation is listed under its first request still shown, so one a sign-in or sign-out emptied reads "No messages yet" while it runs and is dropped once it ends.
- **Reset demo data:** a new conversation keeps what earlier ones changed at the Companies, because a Company's copy of its test customers belongs to the User ID Iris presents. The reset stores a new per-visitor epoch that goes into that User ID (`userFor`), so every Company meets the visitor as a new person and gives a fresh copy on the next connection. Running conversations end, since their Sessions belong to the person before. Locally the Companies share one copy unless `COMPANY_ISOLATION=visitor`, so the reset shows fresh data only on the deployed, per-visitor Companies.

## Sign-in

The callback previously cleared every history entry on successful consent, and the UI polling path independently called `setMessages([])`. First sign-in now snapshots and retains the pre-account conversation (bounded to the existing 10-message model history). Polling renders the server's returned history. Refresh uses the same persisted history.

Later consent may select a different account, so it retains only this public prefix, never private account turns or pending approvals, unless the Company's answers on a conversation that used the account show the sign-in is for the same one (see [permission and consent](permission-consent.md)). Legacy signed-in runs without a recorded public prefix fail closed and do not carry private history across consent. Sign out clears both histories. Messages already discarded by the old behavior cannot be recovered from the run.

Callback regressions cover initial public continuity, immutable copy, later account-context separation, invalid grants and failed consent. Browser fixture test confirmed both prior messages remain after the simulated consent completion; no real grants issued.

## Composer

The run view is a viewport-height flex workspace. Main/conversation/transcript use `min-height: 0` so content can shrink inside the available height; the transcript owns scrolling, not the document. Composer and conversation header do not shrink. Setup scrolls within its own bound when expanded. The introductory heading disappears once the conversation has content; the secondary note/footer do not occupy bottom space in run view. Inspector and Identity retain normal document scrolling.

Height follows `visualViewport.height` when available, with a dynamic viewport fallback and safe-area padding. This supports a shrinking visual viewport, but real mobile keyboard behavior has not been tested on hardware.

Measured browser fixtures:

- 1044×798: composer bottom 798, document height 798; transcript scrollable.
- 390×844: composer bottom 844, document height 844; no horizontal overflow.
- 390×500: composer bottom 500, transcript remains visible (135px).
- New message + fixture reply: composer unchanged at 798 and transcript scrolled to the latest reply.
- Expanded mobile model settings: composer stays at 844; setup becomes scrollable.
