# The agent's core

`packages/pap-agent` (`@poppy-lab/pap-agent`) is the Personal Agent without a channel: conversations with Companies over PAP 1.0, their storage, the model turn and everything around it. The playground's page is one client of it. An OpenAI-compatible API, an MCP server for harnesses such as Claude Code or Codex, messaging channels such as Telegram and a mobile app built outside this repository are meant to be others, all on the same conversations.

It is plain TypeScript with no Next.js import, and runs on Workers and on Node. It uses `@poppy-lab/pap-client` for the protocol and `@poppy-lab/llm-adapters` for the model, which stay packages of their own.

## What is in it

`@poppy-lab/pap-agent` is the channel-neutral API. ## Two layers: the turn, and the API

Every function that does something for a conversation takes a `Caller` and answers a `Reply` (`web.ts`): a status, a JSON body (or a statement's bytes) and its headers. A channel turns its own request into the one and the other into its own response.

- **The page's contract.** `chat`, `account`, `accountView`, `discover`, `signInCallback`, `conversationList` and `conversationAction` take a Fetch `Request` and a cookie jar and answer a `Response`, in exactly the shapes [chat continuity](chat-continuity.md#what-each-route-takes-and-answers) describes. The playground's routes are each three lines: they hand the request and `cookies()` to one of these.
- **The channel-neutral API** (`api.ts`) is the same turns in plainer terms, as typed functions. A channel that isn't the page uses these.

| Function                                                                | What it does                                                                                                                 |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `startConversation(caller, { company? })`                               | A new conversation, with no Company or with the one at `company`, discovered and connected signed out                        |
| `getConversation(caller, id)`                                           | The conversation now: its Companies, what was said, every proposal                                                           |
| `sendMessage(caller, id, { text, company?, model? }, { stream? })`      | The User's message; `company` is a Company the User chose for it. Without it the agent works out which, or asks with choices |
| `answerChoice(caller, id, { answer, model? }, { stream? })`             | The answer one of the agent's choices carries, in place of a message. A choice's label is never sent as words                |
| `decideProposal(caller, id, { proposal, company, revision, decision })` | Approve or decline a proposal, found by its Company and its ID; an approval covers exactly that revision                     |
| `startSignIn(caller, id, { company, access? })`                         | The Company's consent page to open; the agent never sees a password. A client app gets a link instead (`createSignInLink`)   |
| `conversationEvents(caller, id, { signal })`                            | The events that come later: `state` first, then what changes                                                                 |
| `listPending(caller)`                                                   | What waits for the User in every running conversation of theirs: proposals, sign-ins, the agent's open questions             |

Each answers `{ ok: true, value }` or `{ ok: false, status, code?, error }`, where `error` is written for the User and can be shown as it is.

**What goes out.** A message (`AgentMessage`) has its `text` and who it is `from`: `user`, `agent` (with `company` for a turn with that Company, without it in the agent's own voice about the conversation) or `company` (a Company's own words, with their `author`, which a channel shows as the Company's and never as the agent's). It may have `choices` (quick replies, each a `label` to show and an `answer` to send back), `links` (the addresses in the text, with a token or signature in them replaced by "…", as the page shows them), the `steps` of what the agent did and the Companies' exact `data`. An agent's message has `spoken` too: the same in one or two short sentences to read aloud, with no markdown or identifier, amounts as they are said and Company names in full, made by fixed rules from the same words or facts and never by a model (`spoken.ts`), for a voice client such as the iPhone app planned on this API. A turn answers the messages it added, the User's line first, and the conversation's state, with `replaced` when the conversation took back what it showed before (a Company stopped taking the sign-in, a Company was removed). A proposal comes with its exact `terms`, its `revision`, its Company's `summary` as the Company's words, its `state`, when it expires, and `spoken`, what it is in the agent's words from its terms ("Lantern Noodle Bar wants to change your order, for a new total of 88 dollars, 15 more."). The agent's question about new terms names them in its `proposals` (`{ company, proposal, revision }`, kept after the question is answered), so a client that shows a proposal as a card can show it after the message it arrived with and leave it there once decided, as the playground does; the choices stay on the message for a client that shows buttons instead.

**What waits.** `listPending` lists everything that waits for the User across their running conversations (`pending.ts`, `pending-runs.ts`), for a client's inbox: each `PendingItem` has its `conversation`, its `kind` (`proposal`, `signin` for a sign-in to finish or to do again, `question` for the agent's open question: go on with a request, a Company's invitation, a sign-out or a removal to confirm, which Company a request is for), its `company`, a `text` in the agent's words ("Approve or decline the $88.00 change", never the Company's summary), `expiresAt` when it runs out on its own, and a proposal's `id` and `revision`. Decided, answered and expired items, and ended conversations, are left out; nothing secret is in an item (no token, code, verifier or OAuth `state`). The playground's page lists the same for the conversation it shows from its own state (`pendingItems`), and the others' from this.

**The answer as it is written.** A model writes its answer for seconds; the free model takes 9 to 12. `runModel` (`@poppy-lab/llm-adapters/server`) streams it from every provider when given `onText`: the tool steps run as before, and each piece of text is passed on as the model writes it. The words of every step are the answer, a paragraph each, streamed or not, so a line said before a tool call ("I'll look at your orders.") is kept as it was heard. The Workers AI binding streams OpenAI's chunks, each with its own tokens' Neurons and padding, then one event of its older shape with the whole call's usage, then `[DONE]`; its `fetch` takes the usage and the older event out, since the provider would read each chunk's usage as the call's and can't read the older event, and reports the call's Neurons once however the stream ends. A stream that fails, or ends empty, before anything was said or any tool ran is asked again whole; one refused or out of time is not. `sendMessage` and `answerChoice` take a `stream` (`TurnStream`) that is given the answer as it is written, and the agent's own line from before the model (`before`). `answerStream` cuts it into sentences (`sentenceSplitter`: at a stop followed by a space, at a line's end, or, past 220 characters, at the last clause or space, never inside a word; a code block is one piece), each a `message.delta` with the message's ID, its `index`, its `text` and its `spoken` form, and gives the result's agent messages the `id` their sentences went under, sending those the turn didn't stream (demo mode, the agent's own lines) whole in the same shape. A Company's content is never streamed: it keeps its own message in the result (§10.1). Over HTTP a client asks for this with `Accept: text/event-stream` on the message's own request, which answers the sentences and then `turn` with the result (`turnEvents`); the conversation's event stream doesn't carry them, since it reads the stored conversation every two seconds and would bring them in bursts. The page's chat route takes the same header ([chat continuity](chat-continuity.md#what-each-route-takes-and-answers)).

**The agent asks.** Whatever waits for the User becomes a question of the agent's own, a message with `choices`: a proposal to approve ("… Approve it?"), a sign-in or the change permission a request stopped for, whether to go on with that request once it is done, a sign-out the User asked for, a Company's invitation ([Iris asks](chat-workspace.md#iris-asks-and-you-can-answer-in-words)). The User answers with a choice (`answerChoice`) or in words (`sendMessage` with "yes", "no", "approve the Lantern one"), which the agent's code reads, never the model, and only as the answer to the question just asked. A spoken "yes" works the same way once a voice client has it as text. A typed approval goes through the same handler as `decideProposal`. A choice whose answer is `signin` is the client's to carry out: open `startSignIn` for that Company and access; sent back to `answerChoice`, it is answered with the same choice.

**Events.** A sign-in finishes in the Company's tab, a proposal runs out or comes back with new terms, a Company writes in a Direct Conversation: these happen after the turn that answered. They are read from the stored conversation, which every channel and request writes to, so a channel learns of what another did without a message bus. `conversationEvents` reads it every two seconds and says what changed (`eventsBetween`): `message`, `messages.replaced`, `signin.completed`, `signin.failed` (a sign-in under way ended without signing in: declined or failed at the Company, or not back within five minutes), `access.lost`, `signout`, `proposal.created`, `proposal.expired`, `proposal.replaced`, `proposal.updated`, `company.added`, `company.removed` and `conversation.ended`. A proposal's expiry is written nowhere, so it is told from the two readings' times. A Company's message in a Direct Conversation is an event once a request has read it from the Company, as the page's next action does; the stream itself sends nothing to any Company.

## Over HTTP: `/api/v1`

The playground serves the API at `/api/v1` (`app/api/v1/[...path]/route.ts`, which hands each request to `v1` in `api-http.ts`). [`openapi.json`](../packages/pap-agent/openapi.json) describes it for a client app, and `/api/v1/openapi.json` serves that committed file directly; `openapi.ts` generates it with request schemas derived from `src/api-contract`, a test keeps the committed file in step with `openapi.ts`, and another holds every route to it and checks real answers against its schemas, member by member. [poppylab.dev/developers/api](https://poppylab.dev/developers/api) shows the same committed document to a person, built from it at build time (`apps/playground/lib/api-reference.ts`), so an operation or a type regenerated into `openapi.json` is on the page at the next deploy; [/developers/native-client](https://poppylab.dev/developers/native-client) is the guide below as a page, with requests and answers a test holds to the document's schemas.

The conversation routes parse bodies and path parameters with the Zod contracts in `src/api-contract`. A malformed known field gets the common `400 invalid_request` body; unknown request members are dropped, except in `Answer` and `ProposalRef`, which reject unknown members. Validation errors use only messages written by the project and never include submitted values. Conversation IDs, Operations proposal IDs and sign-in tickets each use their own path schema rather than one shared length limit. Tests also submit the native-client examples and every model choice the playground can send to these runtime schemas.

| --------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| `POST /api/v1/conversations`                                    | `{ company? }`                                            | 201 `ConversationState`                                      |
| `GET /api/v1/conversations/{id}`                                |                                                           | `ConversationState`                                          |
| `POST /api/v1/conversations/{id}/messages`                      | `{ text, company?, model? }`                              | `TurnResult`; with `Accept: text/event-stream`, `TurnEvent`s |
| `POST /api/v1/conversations/{id}/answers`                       | `{ answer, model? }`                                      | `TurnResult`; with `Accept: text/event-stream`, `TurnEvent`s |
| `POST /api/v1/conversations/{id}/proposals/{proposal}/decision` | `{ company, revision, decision: "approve" \| "decline" }` | `{ proposal, state }`                                        |
| `POST /api/v1/conversations/{id}/sign-ins`                      | `{ company, access?: "read" \| "write" }`                 | `{ url }`; an app's, `{ url, expiresAt, endUrl }`            |
| `GET /api/v1/sign-ins/{ticket}`                                 |                                                           | 303 to the Company, in the app's browser                     |
| `GET /api/v1/conversations/{id}/events`                         |                                                           | `text/event-stream` of `AgentEvent`                          |
| `GET /api/v1/pending`                                           |                                                           | `{ items: PendingItem[] }`                                   |
| `GET /api/v1/openapi.json`                                      |                                                           | the OpenAPI 3.1 document                                     |

The agent account's routes are listed under [Agent accounts and API sessions](#agent-accounts-and-api-sessions).

`model` is `{ provider, apiKey?, model?, turnstile? }` with the User's own key, or `{ provider: "free", turnstile }` for the deployment's free model, which needs a Turnstile token for the deployment's site key on every turn ([the free model](chat-workspace.md#the-free-model)); without it a turn runs in demo mode, which runs the scripted examples only, and so does a free-model turn without a good token or past its limits, with a line that says why. A turn asked with `Accept: text/event-stream` answers Server-Sent Events: a `message.delta` for each of the agent's sentences as it is written (`{ type, message, index, text, spoken }`; the texts of one message joined are its text, and `spoken` is empty for a sentence with nothing to say), then `{ type: "turn", result }`, the same `TurnResult`, whose agent messages carry the `id` their sentences named, or `{ type: "error", status, code?, error }` when the turn failed after its first sentence; a message the result doesn't hold was taken back. A turn refused before anything was said is answered as without the header. Errors are `{ code?, error }` with the status: 400 refused before anything was sent, 403 not from the playground's own origin, 404 no such conversation for this user, 409 another request holds the conversation, or, for a decision, the Company answered the approval with other terms (`terms_changed`: nothing was performed, and the proposal waits again at a new revision), 410 the conversation has ended and is read-only (`conversation_ended`), or, for a decision, the proposal expired or was already decided (`proposal_expired`). The event stream sends `retry: 3000`, then each event under its `type` as the SSE event name, and a comment after every reading; it closes after five minutes or when the conversation ends, and a client opens it again and starts from the new `state`. A signed-in request's stream asks again every few readings whether its sign-in holds, and within about ten seconds of the session ending or the access token running out or being replaced it sends `session.ended` with `code` (`session_revoked`: sign in again; `invalid_token`: refresh and open it again) and closes. Opening a stream is counted, 30 a minute per source and per account, and an account holds at most ten open at once, on all its devices, and a browser not signed in to an account four (429 `too_many_streams`).

A request is the browser's or a client app's. The browser's is the visitor's, by the playground's cookie, or the agent account's it is signed in to, by its account cookie; one that changes anything must come from the playground's own origin. A client app sends no `Origin` and carries `Authorization: Bearer <access token>` of its device's API session; a token that isn't valid is answered 401 `invalid_token` with `WWW-Authenticate: Bearer error="invalid_token"`. A request from another origin that would change anything is refused 403 before its body is read, whatever it carries.

## Storage

A conversation is one stored value, kept under its user. The core defines the store (`Backend` in `runs.ts`): `get`, a compare-and-set `put` (with the time a value is worth nothing, when it has one), `remove`, `list` by prefix, and a fixed-window `count` for the budgets. Locking a conversation for a request is a compare-and-set on its version, so it holds across Worker isolates.

- A Node process that configures nothing keeps conversations in memory and in the encrypted vault, as local development always has, and the agent accounts and the channels' links with them.
- On Workers the core has no file system and refuses to guess: a channel names its store with `configureStorage(open)`, opened on the first request that needs it, since a Worker's bindings exist only while it serves one. The playground's is the visitor's Durable Object, with every value sealed under `POPPY_STATE_KEY` (`sealedBackend`).
- Tests and a channel with a store of its own can set one directly with `configureBackend`.

What is stored keeps its shape. A conversation stored before the core was a package reads and goes on as before, and `readRun` still reads the shape from before a conversation held several Companies. `apps/playground/app/api/account/stored.test.ts` checks it with two conversations captured as production stores them.

## Identity

Every conversation is kept under an agent user, and a `Caller` says which one a request is for (`user(create)`), whether the channel vouches that the request is that user's own (`authentic`), where the agent is served (`origin`, which says where the lab's Companies are) and how a sign-in is bound to the user who started it (`signIns`: `bind`, `holds`, `release`).

- **The page's visitor** (`browserCaller`): the SHA-256 of the visitor cookie, `authentic` for a same-origin request, and a cookie for each sign-in, sent only to the callback. A browser signed in to an agent account is the account's instead (`Caller.account`, `via: "cookie"`).
- **A client app's device** (`apiSessionCaller`): the agent account its API session belongs to, `authentic` by its bearer token (`via: "bearer"`).
- **A channel's own user** (`channelCaller`, `channelUser`): a Telegram chat, say, is mapped to an agent user the first time the channel names it, kept as a link record of its own in the accounts' store (`link-codes.ts`), so a link lasts as long as its account. Redeeming a link code points that record at an account's agent user (`linkChannelUser`). The channel binds a sign-in in its own way.

## Agent accounts and API sessions

An **agent account** is the person behind any number of browsers, devices and channels. It is an opaque ID, its passkeys and a label the person may choose ("Home"), and nothing else: no email, no password, no name. Its conversations, and the Companies connected in them, are kept under an agent user of its own (`AgentAccount.user`), so every device signed in to it sees the same ones. The anonymous visitor stays: the lab needs no account to try.

**Passkeys** (`passkeys.ts`, with [`@simplewebauthn/server`](https://simplewebauthn.dev)). The relying party is the deployment's host: `poppylab.dev` in production, whatever a request says (`AGENT_PUBLIC_ORIGIN`), and the request's own host in development. Every passkey is discoverable (a resident key), so signing in needs no username: the authenticator's answer names the account by its user handle, which is the account's ID. User verification is required; no attestation is asked for, so nothing is learned about the device. Each ceremony is two requests: the options, with a challenge kept for five minutes and taken once (a compare-and-set, then removed), and the answer. The account keeps each passkey's credential ID, COSE public key, signature counter (a counter that goes back is refused), transports, whether it is synced, where it was added, and when it was added and last used. An account has one to ten passkeys: removing the last is refused (`last_passkey`), checked inside the account's compare-and-set so two devices removing the last two at once leave one. Removing a passkey ends every session it started, on every device, the one asking too: a lost phone's cookie and tokens stop working with it. A sign-in it was in the middle of starts no session.

**API sessions** (`api-sessions.ts`). Each signed-in device has a session of its own, with its device's label ("Chrome on macOS", "iPhone"), when it was created and last used, and the passkey it began with. A browser's session is a cookie (`__Host-poppy_account`, `HttpOnly`, `SameSite=Lax`, 30 days). A client app's is an access token that lasts 15 minutes and a refresh token that is replaced each time it is used; a refresh token shown a second time ends the whole session (`session_revoked`), on that device and wherever the copy is. A session not used for 30 days ends, and every session ends after a year. A token is `poppy_at.<account>.<session>.<secret>` (`poppy_rt`, `poppy_bs` for the others): the IDs find the session with one read and the secret proves it. Only SHA-256 hashes are kept, compared with `timingSafeEqual`; tokens go in headers, cookies and bodies, never in an address or a log. Signing out on one device ends only that device's session. An account keeps at most 25 sessions: signing in on one more device ends the one used least recently. `ApiSession.verified` records when the person last proved they were there with a passkey, for a later step-up.

**Where they are kept** (`account-store.ts`). The same `Backend` as conversations, in buckets of their own: `account:<id>` holds the account (with its passkeys) and a `session:<id>` per device, `ceremony:<id>` a challenge, `link-code:<hash>` a link code, `sign-in-ticket:<hash>` an app's sign-in link and `sign-in-state:<hash>` whose sign-in that link started, by its OAuth `state`. A channel names the store with `configureAccountStorage(open)`; without one, accounts are kept where conversations are. The playground's is a `PoppyAccount` Durable Object per bucket, sealed like the visitor's, which an alarm deletes after a year without use (`apps/playground/worker/visitor.ts`). A ceremony, a link code, a sign-in link and its `state` are written with the time they run out (`put`'s `expires`), so an object holding one goes when it is taken or within minutes, and options anyone can ask for leave nothing behind for long. A Node process that configures nothing keeps the accounts, their sessions and the channels' links in memory and in the encrypted vault, as it keeps conversations, so they outlive a restart; ceremonies, link codes and sign-in links go with the process.

**Bringing a browser's conversations in.** When a browser signs in, its visitor's conversations stay the visitor's: the account's are shown, and the account says how many the browser could bring (`unclaimed`). `POST /api/v1/account/claim` moves them, only when the person asks (`moveConversations` in `runs.ts`). Each keeps its ID, its words, its Companies and the User ID each Company knows; one another request holds right now stays and is counted (`skipped`). Conversations stored before this, in any shape `readRun` reads, move and read the same way.

**Linking a channel** (`link-codes.ts`). A signed-in account asks for a code (`POST /api/v1/account/link-codes`: eight characters without look-alikes, shown as `ABCD-EFGH`, valid five minutes, kept as a hash) and types it into the channel. The channel redeems it once, `redeemLinkCode({ channel, user, code })` in this process or `POST /api/v1/link-codes/redeem` from outside it, and from then on `channelUser(channel, user)` answers the account's agent user. The HTTP route serves only a channel the deployment names with `configureLinkingChannel({ name, authenticate(request) })`; the playground names none, so it refuses every request with 401 `channel_unauthenticated`. No channel adapter is built yet.

**Budgets** (`account-limits.ts`), on every deployment: asking to create an account 5 an hour per source and 60 an hour in all, since with no attestation a script answers as well as a phone, and answering those options 10 a minute per source; signing in 20 a minute per source and per account; managing passkeys, sessions, codes and conversations 30 a minute per source and per account; refreshing 30 a minute per source and per account; redeeming a code 10 a minute per channel user, with a global ceiling; not per source, since a channel server's users share its address; asking for a sign-in link 20 a minute per source and per account, and opening one 20 a minute per source; each with a global ceiling. Signing in and refreshing name their account before anything proves it (the passkey's user handle, the refresh token's prefix), so there the account is counted together with the source: someone who knows an account's ID spends only their own tries at it, never its owner's. The source is counted first, so tries a source was refused spend nothing of the ceiling everyone shares. Over one, the answer is 429 `rate_limited` with `Retry-After` the limit's window in seconds: 60, or 3600 for an hourly one. A source is the `cf-connecting-ip` address, hashed, and only on Workers, where Cloudflare sets it; anywhere else any client can send that header, so a request there has no source and only the per-account and global budgets hold (`clientAddress` in `web.ts`). An IPv6 address counts by its /64.

The account routes use the contracts in `src/api-contract/accounts.ts`. Passkeys and sessions in paths use the agent's 22-character opaque IDs; the longer authenticator credential ID stays inside the bounded WebAuthn response object. Ceremony IDs, refresh tokens, labels, device names, channel users and link codes are validated before their handlers use them. Malformed credentials, tokens and codes receive only project-written `invalid_request` messages, and tests verify that their submitted values reach neither errors nor logs.

Both clients use the same routes. **The page** sends its `Origin` and its cookies: creating an account or signing in sets the account cookie and answers `{ account }` with no token, and every request after that is the account's. **A client app** sends no `Origin`: it is answered `{ account, tokens }`, where `tokens` is `{ session, accessToken, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt }` (milliseconds since 1970), and sends `Authorization: Bearer <accessToken>` from then on. A Company's sign-in comes back to a browser, which binds it to itself with a cookie, so over an API session `POST …/sign-ins` answers a link to a page of the agent's own instead of the Company's consent page (below). Errors are `{ code, error }` as above, with 401 `not_signed_in`, `invalid_token` or `session_revoked`, 400 `invalid_request`, `passkey_not_verified` or `ceremony_expired`, and 429 `rate_limited`. A sign-in that proves no account is answered 400 `passkey_not_verified` whatever the reason (no such account or passkey, a passkey removed, a signature or counter that fails), so the answer doesn't tell whether an account or a passkey exists.

**A Company's sign-in from an app** (`sign-in-links.ts`, §4.2: "When the Personal Agent sends the User a link to open later, … it SHOULD link to a page of its own that pushes the request when the User opens it"). Over an API session, `POST /api/v1/conversations/{id}/sign-ins` checks what the sign-in will need (the conversation is the account's and running, the Company is connected in it and is one the agent may sign in to) and answers `{ url, expiresAt, endUrl }`. `url` is `/api/v1/sign-ins/<ticket>`: 32 random bytes, kept only as a SHA-256 hash, taken once (a compare-and-set), for three minutes, and bound to the account, the device's session, the conversation, the Company and the access asked for. Opening it in a browser takes the ticket and, unless the session has ended since or the browser says it is another account's (an access token of another account, or the playground's account cookie), starts the sign-in there exactly as the page's Sign in does: the request pushed to the Company (PAR) when it offers it, `prompt=consent`, and the sign-in cookie `pap_oauth_<state>` set in that browser. It notes whose the sign-in is under the hash of its `state` (`sign-in-state:`), since that browser has no cookie of the account's, and answers 303 to the Company's authorization endpoint. Anything else ends at `endUrl` with `?result=failed`, and the ticket is spent all the same. The callback finds the note, completes the sign-in for the account's conversation as it does for the page, and sends the browser to `/playground/sign-in/app?result=done` (with `&company=<key>` for one of the lab's Companies, which the page names: "Signed in to Harborline Bank. You can go back to the app.") or `?result=failed`. That address is fixed: the agent never sends the browser to an address a request names. The ticket is in an address, as an OAuth code is, so it is made useless soon instead: the agent never logs it, the Worker turns on no request logs (`wrangler.toml` has no `[observability]`), and a copy is spent or expired within minutes.

The app opens the link at once on the device that asked, so the sign-in doesn't cross to another device. What is left is a link someone forwards (RFC 10027 §6.1), with these limits: it is never shown to the person, it works once and briefly, a browser signed in to another account can't use it, and the Company's own consent page names the agent and is shown every time. The agent shows no page of its own before the Company's: the person has just pressed Sign in in the app, the browser's sheet shows each site's address, and the Company's page, under the Company's own domain, already says which agent asks and for what. A page of the agent's would add a step for every sign-in and would not stop the person a forwarded link is sent to, who would see a page of a site they may trust.

**Left for later.** A device registers for push on its own session (`ApiSession.push`, `PushDevice`: the APNs token, environment and topic), planned as `PUT /api/v1/account/sessions/{id}/push`, so it goes when the session does. A step-up for an approval asks the account's passkey again and checks it against the session's `verified` time.

### A native client (an iPhone app)

The same steps, with a request and an answer for each, are on [poppylab.dev/developers/native-client](https://poppylab.dev/developers/native-client) (`apps/playground/app/developers/native-client/page.tsx`); a change here belongs there too.

An app on iOS creates and uses passkeys for `poppylab.dev` with `ASAuthorizationPlatformPublicKeyCredentialProvider(relyingPartyIdentifier: "poppylab.dev")`, and the API does the rest:

1. **Create an account.** `POST /api/v1/accounts/options` with `{ label? }` and no `Origin`. Pass `options.challenge` and `options.user.id` (both base64url) to `createCredentialRegistrationRequest(challenge:name:userID:)`, with `userVerificationPreference = .required`. Send the result as a `RegistrationResponseJSON` (`id`, `rawId`, `type: "public-key"`, `response.clientDataJSON`, `response.attestationObject`, `response.transports`) to `POST /api/v1/accounts` with the `ceremony` and `device` ("iPhone"). Keep `tokens` in the Keychain.
2. **Sign in on another device.** `POST /api/v1/sessions/options`, then `createCredentialAssertionRequest(challenge:)` with no allowed credentials, so the system offers every passkey for the site, and send the `AuthenticationResponseJSON` (`response.clientDataJSON`, `response.authenticatorData`, `response.signature`, `response.userHandle`) to `POST /api/v1/sessions`.
3. **Call the API** with `Authorization: Bearer <accessToken>`. When it is refused with `invalid_token`, or before `accessTokenExpiresAt`, exchange the refresh token at `POST /api/v1/sessions/refresh` and keep the new pair; refresh once at a time, since a refresh token used twice ends the session. On `session_revoked`, sign in again.
4. **Sign in to a Company.** `POST /api/v1/conversations/{id}/sign-ins` with `{ company, access? }` answers `{ url, expiresAt, endUrl }`. Open `url` at once, and only once, in `ASWebAuthenticationSession(url:callback:completionHandler:)` with `callback: .https(host: "poppylab.dev", path: "/playground/sign-in/app")` (iOS 17.4 and later; it relies on the same `webcredentials:poppylab.dev` association as the passkeys) and `prefersEphemeralWebBrowserSession = true`, so the Company's cookies stay out of Safari and a playground account signed in there can't refuse the link. Send no header: the link needs none. The agent's page goes straight on to the Company's consent page, and the person signs in there. The session completes when the browser reaches `endUrl`, with `result=done` or `result=failed` in the callback URL's query: take it as a hint, and take the outcome from the conversation, `signin.completed` or `signin.failed` on the events, or the Company's `signedIn` in `GET /api/v1/conversations/{id}`. There is no `callbackURLScheme`: the agent sends the browser only to its own fixed address, never to one a client names, so a custom scheme would never be reached. On earlier iOS, open the session without a callback (`callbackURLScheme: nil`): it ends when the person closes the sheet, and the app reads the conversation then. A sheet closed early leaves the sign-in waiting; it ends with `signin.failed` after five minutes, and pressing Sign in again asks for a new link, which replaces it. If a request stopped for the sign-in, the agent then asks whether to go on with it: a `message` on the events with a `resume` choice, which the person presses or answers "yes" to within 30 minutes.
5. **Speak the answer as it is written.** Send a message or an answer with `Accept: text/event-stream` and say each `message.delta`'s `spoken` as it arrives, skipping an empty one; the sentences are the whole answer, so the message's own `spoken` isn't said again when `turn` comes. Show `result` from `turn` in place of the sentences. A response that isn't `text/event-stream` is a refusal, as JSON with its status.
6. **Sign out** with `POST /api/v1/account/sign-out`; the account's other devices stay signed in.

The system only offers an app passkeys for a domain that vouches for it. The app needs the Associated Domains entitlement `webcredentials:poppylab.dev`, and the site must serve `https://poppylab.dev/.well-known/apple-app-site-association` as JSON, with no redirect, listing the app: `{ "webcredentials": { "apps": ["<Team ID>.<bundle ID>"] } }`. The playground serves it (`app/.well-known/apple-app-site-association/route.ts`) for the apps in `APPLE_APP_IDS`, a var in its wrangler.toml (`TEAMID.bundle.id`, separated by spaces), so an app's ID is never written in the code; with none set the route answers 404. A developer build can read it directly with the entitlement `webcredentials:poppylab.dev?mode=developer` and Associated Domains Development turned on in the device's settings. The clientDataJSON an iOS app sends has the origin `https://poppylab.dev`, which the API already expects.

## How a channel plugs in

1. Configure the core once, before the first request: `configureAgent({ name })`, the agent's name in its own sentences, and on Workers `configureStorage(open)`, `configureAccountStorage(open)` and, for the free model, `configureFreeModel({ binding })` with the Workers AI binding.
2. Make a `Caller` for each request: `await browserCaller(request, cookies)` for a browser, `channelCaller({ user: await channelUser("telegram", chatId), origin, signIns })` for a channel with users of its own. `/api/v1` makes an API session's (`apiSessionCaller`) from a bearer token itself.
3. Call the API: `startConversation`, then `sendMessage` or `answerChoice` for each thing the user says or presses; show each message by its `from`, each choice as a button that sends its `answer` (and read `spoken` aloud, in a voice client, or each sentence's as it is written: `stream`), each proposal with its terms and an approve and a decline, beside the agent's question about it, which the User can also answer in words; open `startSignIn`'s `url` for the user (over `/api/v1`, an app opens its sign-in link the same way, in a browser of its own); follow `conversationEvents` while the user is there.

The playground does all of this for its own page through the page's contract, and serves the API for any other client.

**The agent's name** is configuration, never the core's. `configureAgent({ name: "Iris" })` is what the playground passes (`lib/agent.ts`); the model's system prompt and every sentence the agent says in its own voice use it ("Iris connected it to this conversation", "Approved by Iris on your standing instruction"). A page that renders the core's sentences in the browser can't count on that call having run in each bundle, so a build may also give `AGENT_NAME`, which the bundler writes into the code: the playground's `next.config.ts` does. With neither, the agent is called "Agent".

No name on the wire says the agent's name. A chat answer's `mode` for the agent's own words is `"own"`, and the page's message role for them is `"Own"` (`app/playground/companies.ts`): the same word, which says whose words they are, as `ownAnswer` and `own` in the code do, where `"agent"` would also fit an answer to a turn with a Company (`from: "agent"` in the API). They were `"iris"` and `"Iris"`. The page still reads `mode: "iris"` the same until 31 January 2027, for an answer from a Worker rolled back to before the rename; the role was only ever the page's own state, and no stored conversation holds either (`apps/playground/app/api/account/stored.test.ts`), so nothing stored is translated. `/api/v1` never carried them.

## Two modes

- **Full agent.** The core runs its own loop: it picks the Company, calls the model with that Company's tools, keeps the conversation, asks for approvals and signs in. Every channel above uses this mode.
- **Protocol toolbox** (designed here, built later). A harness such as Claude Code or Codex brings its own model and loop and needs the protocol, not another agent. An MCP server would offer the core's pieces as tools: discover a Company, start a Session, list its tasks and tools, call one, read and answer a Company's agent, start a sign-in and wait for it, list the proposals and ask the User to approve one. The core keeps the conversation, the Sessions, the tokens and the proposals, so a token still goes only to the Company that issued it and nothing is performed without the User's approval: approving would never be one of the harness's tools, only asking the User to approve in the channel the User trusts (a link to the playground, say). What the harness is told is the Companies' content as data, as the model is told today.

## Checks

The core's own tests run with `pnpm --filter @poppy-lab/pap-agent test`, and read the agent's sentences as the playground names it. `src/exports.test.ts` checks that every imported `@poppy-lab/pap-agent` subpath matches `package.json` `exports`, that no stale unimported exports remain, and that no production file imports test-only entry points (`@poppy-lab/pap-agent/testing` or `@poppy-lab/pap-agent/openapi`). The playground's tests drive its routes, the stored conversations and `/api/v1` against the core; its end-to-end tests run the lab's real Companies in process.
